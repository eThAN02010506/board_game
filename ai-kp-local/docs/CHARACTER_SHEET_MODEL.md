## 参考样本与设计边界

本设计直接参考用户提供的 `COC空白卡.xlsx`：

- SHA-256：`eeb4ceea026bf172cd3337f42f1815da897c5c7fa46fb61641b83ef146759545`
- 工作簿包含 12 个工作表；主要玩家角色卡位于 `人物卡`，其余工作表用于职业、技能、武器、资产等查表和公式支持。
- 已核对的主要区域：身份 `B2:H8`、属性与状态 `J2:X13`、技能 `B14:X49`、武器 `B51:X58`、资产与物品 `B60:J88`、背景及经历 `L60:AG110`。
- 样本无 VBA 和外部链接，但导入器仍必须把任何工作簿视为不可信输入，禁止运行宏、外部链接和工作簿公式。

Excel 是字段和交互布局参考，不是运行时数据库结构，也不是规则引擎。导入时只读取明确允许的玩家输入和模板标识；所有半值、五分之一值、生命值、魔法值、理智初值、移动力、伤害加值、体格及资产级别等派生结果，都由后端按 [`RULES_REFERENCE.md`](RULES_REFERENCE.md) 指定的规则版本重新计算。

## Excel 所表达的角色卡结构

### 1. 身份与职业

包括调查员姓名、玩家名、时代、职业、年龄、性别或性别描述、居住地、出生地和头像。Excel 中的职业序号及查表单元格属于模板实现细节；系统应保存稳定的职业标识和显示名称，而不是保存行号或单元格公式。

### 2. 基础属性与派生值

玩家或建卡流程产生的基础属性为 `STR`、`CON`、`SIZ`、`DEX`、`APP`、`INT`、`POW`、`EDU` 和幸运。工作簿会计算属性半值与五分之一值，并从属性得到生命值、魔法值、初始理智等数据。

这些计算值必须标记为 `server_computed`。导入预览可以显示“Excel 当前显示值”和“规则引擎重算值”的差异，但保存的权威值只能来自规则引擎。

### 3. 技能

Excel 的技能行同时表达：技能基础值、成长值、职业点、兴趣点、当前总值、半值、五分之一值、成长标记和职业技能标记；带专攻的技能还包含专攻名称。后端统一将其建模为技能列表，而不是左右两块固定表格：

```json
{
  "skill_key": "coc7.fighting_brawl",
  "display_name": "格斗",
  "specialization": "斗殴",
  "base_value": 25,
  "occupation_points": 0,
  "interest_points": 0,
  "development_points": 0,
  "current_value": 25,
  "half_value": 12,
  "fifth_value": 5,
  "growth_mark": false
}
```

基础值、职业/兴趣点来源和特殊技能限制需要规则校验。闪避、母语等依赖属性的基础值也由规则引擎计算。信用评级和克苏鲁神话采用专门约束，不能按普通技能行盲目累加。

`GET /investigator-skills/catalog` 返回服务端权威技能目录。目录记录模板顺序、默认专攻、
固定或属性派生基础值、专攻是否可编辑及创建时是否允许加点。前端不再使用自由文本技能行作为建卡主入口。

`POST /investigator-skills/recommend` 根据职业名称、时代、年龄、九项属性及职业点公式，在本地确定性生成一份完整职业点/兴趣点建议。它不调用大模型，不把建议伪装成规则强制，也不会自动保存；玩家应用后可在双栏完整技能表中逐项调整，再通过现有角色卡保存与 KP 审核流程提交。未知职业回退到通用调查员模板，历史时代排除现代专属技能，且创建时永不为克苏鲁神话加点。

### 4. 武器、资产、物品与背景

武器记录应保存名称、所用技能、伤害表达式、射程、贯穿、每轮攻击数、装弹量和故障值等领域字段；命中率及其半值/五分之一值引用权威技能结果，不复制工作簿公式。

资产区域包含信用评级、现金、其他资产、消费水平、货币和随身物品。背景区域包括外貌、思想与信念、重要之人、意义非凡之地、宝贵之物、特质、关键联结、伤口与疤痕、恐惧症与躁狂症，以及之后可能积累的同伴、神话遭遇、团史和法术。

## 权威领域模型

### 全局调查员与不可变版本

`investigators` 表示玩家拥有、可跨团复用的调查员身份：

- `id`, `owner_player_id`, `ruleset_id`, `name`
- `current_revision_id`
- `created_at`, `updated_at`, `archived_at`

`investigator_revisions` 保存不可变角色卡版本：

- `id`, `investigator_id`, `revision_no`
- `canonical_json`, `public_summary_json`
- `source_type`：`manual` 或 `xlsx`
- `source_hash`, `template_id`, `template_version`, `parser_version`
- `created_by`, `created_at`

角色卡编辑永远创建新 revision，不原地改写已提交或已批准版本。MVP 可先把完整规范化结构放在 `canonical_json`，把身份、所有者、版本和审核关系规范化成表；当技能检索或统计成为性能热点后，再迁移成明细表。

### 每个团独立提交和审批

`campaign_investigators` 表示调查员参与某个团及该团的审批状态：

- `campaign_id`, `investigator_id`
- `submitted_revision_id`, `approved_revision_id`
- `status`：`draft`、`submitted`、`changes_requested`、`approved`、`withdrawn`
- `review_comment`, `reviewed_by`, `reviewed_at`

同一 revision 可提交到多个团，但每个团的 KP 独立批准。KP 退回时必须填写玩家可见的修改意见。玩家修改后提交的是新 revision；上一版已经批准时，该团继续使用上一版，直到新版获批。未批准版本不得进入 AI 上下文或成为该团的可操控角色。

`character_reviews` 作为只追加的审核审计记录，保存操作、目标 revision、角色、理由和时间，不能只保留当前状态。

提交、审批和绑定在写入前取得 SQLite immediate 写事务，审批更新还必须匹配读取时的
`submitted_revision_id + submitted` 状态。因而重提与审批并发时只能形成一种串行顺序，
不会出现“提交指向 v2、审批记录却批准 v1”的撕裂状态。绑定只接受已关联稳定玩家档案、
且档案 ID 与调查员所有者严格相同的活动成员；绑定成功时同一事务同步其 claimed seat
的 `assigned_pc_id`。

### 团内动态状态与永久成长

`investigator_campaign_state` 保存参与团后的可变状态：

- 当前 HP、SAN、MP、幸运；临时疯狂、伤势和其他状态；
- 团内物品、现金和弹药变化；
- 技能成长标记、尚未结算的成长和状态版本；
- 当前游戏世界时间及最后一个权威事件 ID。

这些变化属于团内状态，不修改已批准角色卡 revision，也不因 HP 或 SAN 改变而重新触发整张卡审核。每次变化必须来自可重放规则结果、已批准事件或记录过理由的 KP 裁定。

永久属性变化、技能成长、疤痕、重要关系、法术和主要经历在团内先作为事件记录。到团后或明确里程碑时，系统生成“永久变更提案”，玩家确认后形成新的全局 revision；后续团使用该版本仍按该团的 KP 审核规则处理。

同一调查员跨团时保留使用的 revision 和角色时间线位置。主时间线同一时刻只允许一个
进行中的团；数据库的部分唯一索引与审批事务共同保证该约束。玩家如果确实需要并行参团，
必须先显式建立 timeline branch，并在提交时选择分支，系统不会默默合并相互矛盾的状态。

跨团时间线是参团记录、玩家可见记忆、可见来源事件、NPC 接触和已接受永久变化的读取
投影，不是第二套可写事实。旧团 `kp`/`secret` 事件、隐藏记忆、KP 裁定依据和玩家未亲历
信息不会进入玩家或继任 KP 的投影。每个团的 HP、SAN、MP、Luck、条件与临时物品差异均
重新从该团批准的 revision 初始化。

永久变化必须引用当前团已经落地的来源事件。KP 只能提出候选，玩家以当前
`expected_revision_id` 接受或拒绝；接受会在同一事务创建 `origin_type=milestone` 的
不可变 revision 并切换全局调查员版本，拒绝不会修改角色卡。重复相同决定幂等返回，
相互冲突的决定或过期版本返回冲突。

### 导入审计

`character_imports` 至少保存：

- 原文件名、内容哈希、模板 ID/版本、解析器版本；
- 识别出的工作表和字段映射，不保存可执行公式；
- 缺失字段、未知专攻、非法数值、规则重算差异和其他警告；
- 生成的草稿 revision、导入者和时间。

原始 Excel 可以作为可选的本地私有附件保存，但不能通过玩家公开接口下载，也不能作为后续游戏状态的权威来源。

### 三层校验报告

角色卡预览先规范化输入并重算派生值，再生成三个互不混淆的校验层：

- `structure`：字段容器、必填身份、属性及技能行是否可被规范化；
- `ruleset`：职业点、兴趣点和克苏鲁神话等 CoC7 确定性建卡约束；
- `review_policy`：超出常规范围但允许 KP 根据团规作决定的年龄、属性和技能值。

每项问题包含稳定 `code`、字段 `path`、严重程度和
`requires_kp_review`。旧版 `warnings` 由结构化报告推导，不能成为第二套判断逻辑。
规范化器只计算规范结构，规则集校验器不执行审批，KP 的批准或退回命令由应用层
团务策略验证后再交给持久化层。

## 规范化角色卡 JSON

`canonical_json` 采用版本化 schema，至少分为：

- `identity`：姓名、时代、职业、年龄、性别描述、居住地、出生地、头像资产；
- `characteristics`：八项属性及幸运的建卡值和规则来源；
- `derived`：属性半值/五分之一值、最大 HP/MP、初始 SAN、MOV、DB、体格等只读结果；
- `skills`：稳定技能键、专攻、基础值、职业点、兴趣点、成长值及权威总值；
- `combat`：武器、护甲和建卡时的战斗相关字段；
- `assets`：信用评级、现金、其他资产、消费水平和物品；
- `background`：Excel 背景区域及关键联结；
- `mythos`：典籍、法术和神话遭遇，支持 KP/玩家可见性；
- `relationships`、`campaign_history`：跨团人物关系和主要/支线经历摘要；
- `visibility`：公开、本人、KP 和剧透字段；
- `provenance`：规则集、模板、字段来源和解析版本。

当前 HP/SAN/MP、临时状态和团内物品变化不放入全局 revision 的权威部分；读取游戏角色时，由“已批准 revision + 当前 campaign state”组合得到视图。

## 玩家建卡与 Excel 导入页面

独立路由建议为 `/investigators`，不要求玩家先加入某个团才创建角色。页面按 Excel 的心智模型拆为以下步骤：

1. 身份、时代、职业与头像；
2. 属性、年龄调整和只读派生值预览；
3. 职业技能与剩余职业点；
4. 全技能表、专攻、兴趣点和剩余兴趣点；
5. 武器、资产、物品；
6. 背景、关键联结和初始关系；
7. 规则校验、公开摘要和最终预览；
8. 选择团并提交该 revision 给 KP。

Excel 导入向导为：上传文件 → 识别模板 → 读取允许字段 → 后端重算 → 展示字段映射、差异和警告 → 保存为草稿 → 玩家确认并提交。导入失败不能留下半成品角色或覆盖旧版本。

KP 审核页显示角色卡完整内容、与上次提交/批准版本的字段级 diff、规则警告和原始导入来源。操作只有“批准”和“退回修改”；退回必须写意见。其他玩家只能读取 `public_summary_json`。

## 实施顺序与逐阶段真实验收

### C1：模型与导入预览

- 新增全局调查员、不可变 revision、导入审计和确定性派生值服务。
- 用这份空白卡验证模板识别；再复制一份填写最小合法角色，验证身份、属性、技能、武器和背景映射。
- 修改 Excel 中一个公式显示值，确认系统报告差异且仍采用后端重算值。
- 导入未知模板、缺字段和越界值，确认只生成可修正预览，不污染数据库。

当前用户提供的 `COC空白卡.xlsx` 已通过生产预览接口验收：识别模板
`coc-character-sheet-cn-people-card-v1`，忽略并重算 381 个公式单元格，返回完整 67
项技能与 9 条可修正警告；源文件 SHA-256 为
`eeb4ceea026bf172cd3337f42f1815da897c5c7fa46fb61641b83ef146759545`。

### C2：玩家建卡页面

- 完成 `/investigators` 列表、分步编辑、剩余点数和规则提示。
- 真实测试：玩家从空白表单建一名调查员；另一个玩家无法读取私有详情；重启前后草稿一致。

### C3：按团提交与 KP 审批

- 完成 `campaign_investigators`、审核审计、版本 diff 和权限接口。
- 真实测试：玩家提交 v1，KP 退回并写意见，玩家提交 v2，KP 批准；AI 只能读 v2。之后玩家创建 v3 时，团内仍使用 v2，直至 v3 获批。

### C4：团内状态与跨团时间线

- 已完成 campaign state、事件驱动变化、永久变更提案、玩家决定、显式分支和数据库级
  活动时间线冲突保护。
- 真实测试：角色在本 A 损失 HP、提升技能并结识 NPC；本 A 结束后确认永久变更，再提交本 B。确认临时伤势不错误继承，而永久成长、主要/支线经历及符合条件的 NPC 关系可以被检索。

## 当前代码迁移说明

`player_characters` 现在只作为旧事件、地图棋子和部分投影所需的兼容 PC 身份；它不再是
玩家可直接创建或分配的角色卡权威。公开直接创建 PC、成员 `assign-pc` 与席位
`PATCH .../pc` 均返回 `410 Gone`。权威链路是玩家拥有的 `investigators`、不可变
revision、当前团 `campaign_investigators.approved_revision_id` 与团内可变状态；KP
批准时才建立兼容 PC 投影。删除旧表和外键仍需单独的数据迁移版本，不能在兼容引用
存在时直接清表。
