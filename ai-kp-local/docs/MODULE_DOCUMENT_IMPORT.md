# KP 本文档导入边界

## 用户入口

面向 KP 的导入页面只接受：

- PDF（`.pdf`）
- Word Open XML（`.docx`）

旧式二进制 Word `.doc` 不直接解析。界面应提示用户使用 Word 或 LibreOffice 另存为
`.docx`，避免在主服务中执行不受信任的 Office 转换器。图片文件不作为独立 KP 本
上传，但 PDF/DOCX 内嵌的照片、地图、扫描线索和插图必须被保留。

现有纯文本模组 API 是内部切块与权限基础，不代表最终产品允许上传 TXT、Markdown、
HTML 或其他文件。

## 导入产物

一次导入产生一个不可变来源版本，并拆成两类相互关联的资产：

1. 文本块：正文、标题层级、表格文字、页码或段落范围。
2. 图片资产：原始图片字节、媒体类型、尺寸、来源页码或 DOCX 锚点、附近标题与图注。

OCR 和视觉摘要是可重建的派生数据，不能替代原图。每个派生结果必须记录解析器版本、
模型 ID、生成时间和对应图片哈希。

文本和图片解析完成后，AI 可以提出结构化知识候选，但不能直接宣布为事实：

- `module_canon`：模组明确给出的真相、人物、地点和约束。
- `module_anchor`：必须保持可发现或可参与的关键线索、冲突和叙事功能。
- `reference`：背景说明、气氛、例子和可选素材。

所有候选都保留原始 chunk、图片、页码或 DOCX 锚点，由 KP 审核后进入模组知识层。
`module_anchor` 表示保持叙事功能可达，不表示必须在固定场景、固定时间强制发生。

## 图片处理

处理顺序：

1. 安全校验文件签名、压缩包展开上限、页数、总像素和单图大小。
2. 提取原图并计算稳定哈希；重复图片只存一份，但保留所有出现位置。
3. 对包含文字的扫描件运行 OCR。
4. 可用多模态模型时生成客观视觉摘要，例如人物、场所、线索物件和地图类型。
5. 没有 OCR 或视觉模型时，将图片标记为 `pending_analysis`，整本文档仍可完成导入。
6. KP 在正式入库前预览并修正标题、章节、图片说明和秘密范围。

视觉理解不能自行宣布规则事实或剧情真相。它只生成候选描述，由结构化导入流程和 KP
确认后进入可检索知识。

## 剧透与访问控制

- 文本块与图片默认继承所在章节的可见性和剧透标签。
- 图片 OCR、图注和视觉摘要继承原图权限，不能因成为“搜索文本”而放宽访问。
- 玩家接口不能返回未揭示图片的元数据、缩略图、OCR 文本或存在性线索。
- AI KP 检索结果必须携带来源位置和可见性，不能把未来章节自动加入当前上下文。

## Real-case 验收

每阶段都使用一份含正文、章节标题、表格、普通照片、扫描手写线索和地图的 PDF 与
DOCX 测试：

1. 上传预检：拒绝伪装扩展名、超限文件和 `.doc`，不留下半成品记录。
2. 文本解析：章节顺序、页码/段落锚点和表格内容可追溯。
3. 图片提取：原图、缩略图、重复引用和附近图注正确。
4. 无视觉模型：导入成功，图片显示待解析。
5. 有视觉模型：OCR/摘要保存模型来源，重新分析不会覆盖原始证据。
6. 权限验证：玩家无法通过列表、搜索、直接资源地址或实时事件发现秘密图片。
7. 重启恢复：来源文件、解析版本、图文关系和 KP 修订均能恢复。
